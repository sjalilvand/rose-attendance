# راهنمای نصب، راه‌اندازی و کار با سامانهٔ «رز سفید»

**نسخهٔ ۲٫۱ — آبان ۱۴۰۵ (اکتبر ۲۰۲۶)** · مخزن: `github.com/sjalilvand/rose-attendance`

این سند راهنمای عملیاتی گام‌به‌گام برای نصب سامانه روی سرور، به‌روزرسانی دوره‌ای، پشتیبان‌گیری، فعال‌سازی اپ اندروید و آموزش کار روزمره به تفکیک نقش است. مبانی طراحی و قواعد کسب‌وکار در «سند جامع نیازمندی‌ها و معماری» (docs/REQUIREMENTS.md، §۳۴ نسخهٔ ۲٫۱) آمده و در اینجا تکرار نمی‌شود.

---

## ۱. معرفی و معماری

سامانهٔ حضور و غیاب «رز سفید» یک راه‌حل کامل RTL فارسی با تقویم جلالی برای شبکهٔ شعب (طراحی برای حدود ۸۵۰ شعبه و ۸٬۵۰۰ پرسنل) است. کارکنان با PWA یا اپ اندروید تردد و درخواست ثبت می‌کنند، مدیران شعبه/منطقه در صف رسیدگی تصمیم می‌گیرند و منابع انسانی گزارش‌های ماهانه، انتظامی و سالانه را خروجی می‌گیرد. همهٔ تقویم‌های برنامه (انتخابگر تاریخ، جدول کارکرد، گزارش‌ها، اپ اندروید) شمسی‌اند و ساعت مرجع همهٔ محاسبات `Asia/Tehran` است.

استقرار با Docker Compose انجام می‌شود و از هفت سرویس تشکیل شده است:

| سرویس | تصویر پایه | نقش |
|---|---|---|
| `db` | postgis/postgis:16-3.4 | پایگاه‌دادهٔ PostGIS (ژئوفنس شعب + دادهٔ عملیاتی) |
| `redis` | redis:7.4-alpine | صف Celery + لایهٔ کانال WebSocket |
| `api` | rose-attendance-backend | Django + DRF + Channels (gunicorn/uvicorn) |
| `worker` | همان تصویر backend | مصرف صف (محاسبات سنگین گزارش‌ها) |
| `scheduler` | همان تصویر backend | زمان‌بند Celery Beat (نگهداشت و پاک‌سازی) |
| `gateway` | nginx:stable-alpine | فرانت PWA (build شده) + پروکسی api/ws + TLS |
| `migrate` | همان تصویر backend | اجرای یک‌بارهٔ مهاجرت‌ها در هر استقرار |

آدرس‌های اصلی پس از استقرار: وب‌اپ `http://localhost/`، سلامت سرویس‌ها `http://localhost/api/v1/health/`، پنل ادمین `http://localhost/admin/` و سوکت اعلان‌ها `/ws/notifications/`. کلاینت‌های PWA و اندروید هر دو از JWT با refresh خودکار استفاده می‌کنند و حساب پس از پنج ورود ناموفق موقتاً قفل می‌شود.

چند قاعدهٔ کسب‌وکاری که در کار روزمره مدام ظاهر می‌شوند و بهتر است قبل از آموزش پرسنل بدانید:

- **تقویم جلالی همه‌جا:** همهٔ تاریخ‌های نمایش و ورودی‌های تاریخ شمسی هستند؛ ذخیره‌سازی داخلی میلادی است و کاربر هرگز با تاریخ میلادی روبه‌رو نمی‌شود.
- **NEEDS_REVIEW:** هر ترددی که موقعیت/ساعتش مشکوک باشد (خارج از ژئوفنس، دقت پایین، بدون مختصات، افست ساعت) رد نمی‌شود؛ به صف رسیدگی مدیر شعبه می‌رود.
- **شکست بازهٔ چندشعبه‌ای:** درخواست مرخصیِ پوشش‌دهندهٔ چند شعبه به «پاره‌های (شعبه × بازه)» شکسته می‌شود و هر شعبه مستقل تصمیم می‌گیرد؛ وضعیت کل پس از آخرین تصمیم قطعی می‌شود.
- **GPS فقط متادیتا:** ثبت تردد هرگز به موقعیت مشروط نیست؛ نبود GPS برچسب UNAVAILABLE می‌گیرد و وارد رسیدگی می‌شود.

## ۲. پیش‌نیازها

برای استقرار تولید روی یک سرور اختصاصی، سخت‌افزار پیشنهادی برای مقیاس هدف حداقل ۴ هستهٔ CPU، ۸ گیگابایت RAM و ۸۰ گیگابایت SSD است؛ برای آزمایش داخلی، یک ماشین ۲ هسته‌ای با ۴ گیگابایت RAM کافی است. حجم دادهٔ عملیاتی با سیاست نگهداشت سه‌ماهه کنترل می‌شود و رشد آن تقریباً خطی با تعداد پانش روزانه است.

نرم‌افزارهای لازم: **Git**، **Docker Desktop** (ویندوز) یا **Docker Engine + Compose plugin** (لینوکس) و در ویندوز PowerShell نسخهٔ ۵٫۱ به بالا (پیش‌فرض ویندوز ۱۰/۱۱/Server). اگر سرور پشت پروکسی یا در شبکهٔ محدود است، مطمئن شوید دسترسی به `registry-1.docker.io`، `dl.google.com` و `pypi.org` برقرار است؛ خطاهای موقت شبکه در build با اجرای مجدد `update.ps1` حل می‌شود.

پورت‌های موردنیاز: ۸۰ (HTTP) و ۴۴۳ (HTTPS) روی فایروال، به‌علاوه هیچ پورت دیگری نباید به بیرون باز شود؛ دیتابیس و ردیس فقط در شبکهٔ داخلی compose هستند.

## ۳. نصب اولیه گام‌به‌گام

نصب اولیه روی یک سرور تازه کمتر از نیم‌ساعت طول می‌کشد. ترتیب دقیق مراحل را رعایت کنید:

```text
1) git clone https://github.com/sjalilvand/rose-attendance.git
2) cd rose-attendance
3) copy .env.example .env      (ویندوز)  |  cp .env.example .env (لینوکس)
4) ویرایش .env  →  DJANGO_ALLOWED_HOSTS=دامنه-یا-IP,localhost,127.0.0.1
                    DJANGO_CSRF_TRUSTED_ORIGINS=https://دامنه,http://localhost
5) .\update.ps1                (ویندوز)  |  bash-like: docker compose build && up && migrate
6) ساخت کاربر مدیر اولیه (بخش ۳.۳)
7) ورود به وب‌اپ و ایجاد ساختار سازمانی (بخش ۱۰)
```

### ۳.۱ فایل `.env`

کلیدهای مهم `.env.example`: `DJANGO_ALLOWED_HOSTS` (دامنه‌های مجاز جدا با کاما — این همان جایی است که دامنهٔ واقعی یا IP سرور را می‌گذارید)، `DJANGO_CSRF_TRUSTED_ORIGINS` (با scheme کامل)، `DB_NAME` و `DB_USER` و `BUSINESS_TIME_ZONE=Asia/Tehran`. رمز دیتابیس و SECRET_KEY جنگو را دستی تنظیم نمی‌کنید؛ اسکریپت استقرار آن‌ها را در پوشهٔ `secrets/` با مقادیر تصادفی ۴۸ بایتی می‌سازد (`secrets/db_password.txt` و `secrets/django_secret.txt`). این پوشه را در پشتیبان‌گیری سرور حتماً همراه کنید.

### ۳.۲ اجرای `update.ps1` — چه اتفاقی می‌افتد؟

اسکریپت چهار مرحله را انجام می‌دهد: دریافت تغییرات با `git pull --ff-only` (اگر مخزن محلی دستکاری شده باشد متوقف می‌شوید)، آماده‌سازی خودکار secrets و `.env`، `docker compose build` + `docker compose up -d` (هفت سرویس) و در پایان `docker compose run --rm migrate` برای مهاجرت‌ها. خروجی سالم این شکلی است: کانتینر db و redis می‌رسند به Healthy، migrate با پیام «No migrations to apply» یا اعمال مهاجرت‌ها تمام می‌شود، api می‌رسد به Healthy و در پایان «بروزرسانی کامل شد ✓» چاپ می‌شود.

### ۳.۳ ساخت کاربر مدیر اولیه

```powershell
$env:DJANGO_SUPERUSER_PASSWORD="رمز-دلخواه"; docker compose run --rm migrate python manage.py createsuperuser --noinput --username admin
```

پرچم `--email` پشتیبانی نمی‌شود؛ ایمیل بعداً از پنل ادمین قابل ویرایش است. برای تغییر رمز admin موجود: `docker compose run --rm migrate python manage.py changepassword admin`. توجه: حساب admin یک «حساب سیستمی» بدون پروندهٔ پرسنلی است؛ برای استفاده از امکانات عملیاتی (تردد، درخواست، پیام) باید برایش پروندهٔ پرسنلی ساخته و وصل کنید یا از حساب‌های واردشده از Excel استفاده کنید.

## ۴. به‌روزرسانی دوره‌ای

فلو استاندارد به‌روزرسانی — که در تمام مراحل توسعه بارها اجرا و تأیید شده — دو دستور است:

```powershell
git pull --ff-only
.\update.ps1
```

پس از هر به‌روزرسانی فرانت‌اند، در مرورگر یک بار **Ctrl+Shift+R** بزنید تا Service Worker جدید جایگزین شود؛ در غیر این صورت ممکن است نسخهٔ کش‌شدهٔ قبلی نمایش داده شود. دو سوییچ کمکی وجود دارد: `.\update.ps1 -SkipPull` (فقط بازسازی سرویس‌ها بدون pull) و `.\update.ps1 -SkipDocker` (فقط pull + راهنمای دستی برای حالت بدون داکر).

اگر `git pull` شکست خورد (تغییرات محلی)، محتوا را موقتاً کنار بگذارید: `git stash` و دوباره pull کنید. اگر build تصاویر به دلیل خطای شبکهٔ موقت شکست خورد، کافی است دوباره `.\update.ps1` اجرا کنید؛ لایه‌های کش‌شده سرعت کار را بالا می‌برند.

## ۵. دامنه، HTTPS و امنیت

برای انتشار واقعی روی دامنه، سه کار لازم است. نخست، در `.env` مقدار `DJANGO_ALLOWED_HOSTS` را به دامنهٔ واقعی تغییر دهید (مثلاً `attendance.example.com,localhost,127.0.0.1`) و `DJANGO_CSRF_TRUSTED_ORIGINS` را با scheme کامل (`https://attendance.example.com`) به‌روز کنید. دوم، گواهی TLS را در مسیر `deploy/tls/` قرار دهید (ساختار و دستورالعمل در همان پوشه آمده است) — پیکربندی nginx گیت‌وی هر دو حالت HTTP و HTTPS را از قبل دارد و بر اساس وجود گواهی، خودش حالت امن را فعال می‌کند. سوم، روی فایروال فقط ۸۰ و ۴۴۳ را باز نگه دارید.

دو نکتهٔ امنیتی مهم برای انتشار: در `.env` مقدار `DJANGO_DEBUG=False` بماند، و پرچم `usesCleartextTraffic` اپ اندروید (که فعلاً برای تست LAN روشن است) پیش از انتشار همراه با تغییر `API_BASE` به HTTPS حذف شود (بخش ۷).

### ۵.۱ ورود یکپارچه (SSO) و پروفایل کاربران

سامانه از **ورود یکپارچهٔ سازمانی با استاندارد OpenID Connect** پشتیبانی می‌کند — یعنی هر ارائه‌دهنده‌ای که صفحهٔ کشف (`/.well-known/openid-configuration`) دارد: Keycloak، Azure AD/Entra، Google Workspace، Authentik، Zitadel و موارد مشابه. کارمند علاوه بر نام‌کاربری/گذرواژه می‌تواند با دکمهٔ «ورود با سامانهٔ سازمانی» در صفحهٔ ورود PWA، با همان حساب سازمانی وارد شود. تا وقتی مقادیر SSO در `.env` خالی باشند، دکمه نمایش داده نمی‌شود و ورود با گذرواژه سر جای خود است.

راه‌اندازی در چهار قدم:

1. در ارائه‌دهندهٔ SSO خود یک «اپلیکیشن» (Client) از نوع Confidential با فلو `Authorization Code` بسازید.
2. **Callback URI** زیر را در همان اپلیکیشن ثبت کنید (دقیقاً با همین شکل):
   `https://<دامنهٔ شما>/api/v1/auth/sso/callback/`
3. در `.env` کنار مخزن این مقادیر را پر و سپس `.\update.ps1` را اجرا کنید (تغییر `.env` با این اسکریپت به سرویس‌ها اعمال می‌شود):
   ```ini
   SSO_ENABLED=1
   SSO_ISSUER=https://sso.example.com/realms/rose      # آدرس پایهٔ ارائه‌دهنده
   SSO_CLIENT_ID=rose-attendance
   SSO_CLIENT_SECRET=...                                # راز اپلیکیشن
   SSO_LABEL=سامانهٔ سازمانی                             # متن دکمهٔ ورود
   SSO_ADMIN_EMAILS=boss@example.com                    # اختیاری: ادمین خودکار
   ```
4. بعد از آپدیت، PWA را با `Ctrl+Shift+R` تازه کنید؛ دکمهٔ SSO باید زیر فرم ورود ظاهر شود.

رفتار سامانه با کاربر تازهٔ SSO: اگر نام‌کاربری برابر ایمیل او از قبل موجود باشد، حساب به هویت SSO **پیوند** می‌خورد (تکراری نمی‌شود)؛ وگرنه بسته به `SSO_AUTO_PROVISION=1` یک حساب «پرسنل» ساخته می‌شود و مدیر بعداً شعبهٔ اصلی و پروندهٔ پرسنلی را از پنل ادمین/سازمان به او نسبت می‌دهد. ایمیل‌های داخل `SSO_ADMIN_EMAILS` به‌طور خودکار ادمین می‌شوند. امنیت فلو: ورود با `state` یک‌بارمصرفِ ۱۵دقیقه‌ای انجام می‌شود، راز client فقط در سرور می‌ماند و توکن‌ها از طریق fragment مرورگر (#) برگردانده و بلافاصله پاک می‌شوند.

**صفحهٔ پروفایل** برای همهٔ کاربران فعال است: با زدن «نشان نام» در بالای صفحه (کنار دکمهٔ خروج) صفحهٔ پروفایل باز می‌شود و شامل مشخصات کامل (کد پرسنلی، شعبهٔ اصلی، عنوان شغلی، نقش‌ها، شعب مجاز، روش ورود، آخرین ورود)، ویرایش شمارهٔ موبایل توسط خود کارمند، و تغییر گذرواژه است (برای کاربران SSO این بخش با پیوند راهنمای سامانهٔ سازمانی جایگزین می‌شود).

## ۶. پشتیبان‌گیری و بازیابی

منبع حقیقت سامانه یک volume داکری متعلق به سرویس `db` است. پشتیبان منطقی روزانه با pg_dump کافی و استاندارد است:

```powershell
# پشتیبان‌گیری (ویندوز؛ در لینوکس همین دستور بدون cmd)
docker compose exec -T db pg_dump -U rose_app rose_attendance > backup-%DATE%.sql
```

```powershell
# بازیابی روی سرور تازه (پس از update.ps1 و مهاجرت‌ها)
type backup-2026-10-24.sql | docker compose exec -T db psql -U rose_app -d rose_attendance
```

برای خودکارسازی، یک Task Scheduler ویندوز بسازید که هر شب این دستور را اجرا و فایل را به مسیر شبکه/دیسک دوم منتقل کند (در لینوکس cron). فرکانس پیشنهادی: روزانه کامل؛ نگهداری حداقل ۳۰ نسخه. علاوه بر SQL، دو چیز را همیشه همراه پشتیبان نگه دارید: پوشهٔ `secrets/` (بدون آن api بالا نمی‌آید) و فایل `.env`.

برای انتقال کامل به سرور جدید: مخزن را clone کنید، `secrets/` و `.env` را کپی کنید، volume دیتابیس را با `docker run --rm -v rose-attendance_db-data:/from ...` یا با بازیابی SQL منتقل کنید و در پایان `update.ps1` بزنید. سیاست نگهداشت عملیاتی (پاک‌سازی رویدادها و پیام‌های قدیمی‌تر از ۳ ماه) با `RETENTION_MONTHS=3` در `.env` کنترل می‌شود و کلید `CLEANUP_ENABLED` پس از تأیید سیاست پاک‌سازی فعال می‌گردد.

## ۷. اپ اندروید و فعال‌سازی CI

اپ اندروید (Kotlin/Jetpack Compose، RTL قفل‌شده، تقویم جلالی بومی) شامل ثبت ورود/خروج با موقعیت مکانی، تاریخچهٔ کارکرد، درخواست مرخصی، رسیدگی مدیران و پیام‌هاست. ساخت APK به‌صورت ابری با GitHub Actions انجام می‌شود و به نصب Android Studio روی هیچ ماشینی نیاز ندارد.

**فعال‌سازی یک‌بارهٔ CI (سه قدم وب، بدون نیاز به توکن):**

```text
1) در گیت‌هاب، صفحهٔ مخزن را باز کنید → Add file ← Create new file
2) نام فایل را دقیقاً وارد کنید:  .github/workflows/android.yml
   (با تایپ اسلش، پوشه ساخته می‌شود)
3) محتوای فایل android/ci/android-build.yml را کپی و Paste کنید و Commit بزنید
```

از این پس هر تغییر در مسیر `android/**` (یا اجرای دستی دکمهٔ Run workflow) یک ران می‌سازد که `app-debug.apk` را در بخش Actions ← ران ← **Artifacts** قرار می‌دهد؛ APK را دانلود و روی گوشی نصب کنید (نصب از منابع ناشناس را موقتاً مجاز کنید).

**تنظیم آدرس سرور اپ:** مقدار `API_BASE` در `android/app/build.gradle.kts` تعیین می‌کند اپ به کدام سرور وصل شود: شبیه‌ساز اندروید به `http://10.0.2.2/` (localhost میزبان)، گوشی روی همان شبکه به `http://IP-سرور/` و انتشار نهایی به آدرس HTTPS دامنه. پس از هر تغییر، commit و push کنید تا CI دوباره APK بسازد. پیش از انتشار واقعی، TLS سرور را فعال و `usesCleartextTraffic="true"` را از AndroidManifest حذف کنید.

**مجوز موقعیت:** اپ در نخستین ثبت تردد مجوز GPS می‌گیرد. اگر کاربر رد کند یا موقعیت در مهلت کوتاه نیاید، رویداد **بدون مختصات ثبت می‌شود** (نه رد) و با برچسب UNAVAILABLE وارد صف رسیدگی می‌شود — این رفتار آگاهانه است و نباید به کاربران گفته شود «بدون GPS نمی‌شود ثبت کرد».

## ۸. راهنمای کار — کارمند

**ورود:** با نام کاربری/رمز از صفحهٔ اول PWA یا اپ اندروید. اگر سازمان شما ورود یکپارچه (SSO) را فعال کرده باشد، دکمهٔ «ورود با سامانهٔ سازمانی» هم در صفحهٔ ورود PWA هست (بخش ۵٫۱). پنج ورود ناموفق، حساب را موقتاً قفل می‌کند (پیام «حساب موقتاً قفل است»)؛ بعد از انقضای مهلت خودبه‌خود باز می‌شود. پس از ورود، توکن‌ها خودکار تازه‌سازی می‌شوند و نیازی به ورود مجدد روزانه نیست. **پروفایل:** نام و نقش شما بالای صفحه کنار دکمهٔ خروج نمایش داده می‌شود؛ با زدن آن، صفحهٔ پروفایل (مشخصات کامل، ویرایش موبایل، تغییر گذرواژه) باز می‌شود.

**ثبت تردد:** در تب «ثبت تردد» دکمهٔ ورود/خروج را بزنید. مرورگر موقعیت می‌گیرد؛ اگر در محدودهٔ ژئوفنس شعبه نباشید رویداد ثبت ولی برچسب می‌خورد و به رسیدگی مدیر می‌رود — نیازی به تلاش مکرر نیست. نتیجه (در محدوده/خارج از محدوده/ارسال نشد) بلافاصله زیر دکمه نمایش داده می‌شود. در اپ اندروید همین جریان با دکمه‌های «ثبت ورود/ثبت خروج» انجام می‌شود و برچسب موقعیت دقیق‌تر است.

**کارکرد (جدول جزییات روزانه):** تب «کارکرد» برای هر روز شمسی یک سطر کامل دارد: تاریخ، شیفت، ورود، خروج، کارکرد، استراحت، تأخیر، تعجیل، اضافه‌کاری، غیبت و وضعیت (تعطیل/در انتظار/باز/غایب + مرخصی و مأموریت همان روز). با دکمه‌های «ماه قبل/ماه بعد» جابه‌جا شوید؛ پنجرهٔ نگهداشت سه ماه شمسی است. ستارهٔ کنار اضافه‌کاری یعنی «پیشنهادشده و در انتظار تأیید».

**خلاصهٔ ماه:** تب «خلاصه ماه» جمع‌های ماه جلالی جاری را نشان می‌دهد — مرجع سریع برای چک کردن مانده و مجموع کارکرد قبل از پایان ماه.

**درخواست مرخصی/مأموریت:** تب «درخواست» دو زبانه دارد. تاریخ شروع/پایان با انتخابگر شمسی (روز/ماه/سال) وارد می‌شود و پیش‌فرض «امروز ۰۹:۰۰ تا ۱۷:۰۰» است؛ فقط ساعت را اگر لازم شد عوض کنید. درخواست‌های چندشعبه‌ای خودکار به پاره‌های جدا شکسته می‌شوند و وضعیت هر پاره مستقل نمایش داده می‌شود. درخواست‌های «در انتظار» تا پیش از تصمیم قابل لغو هستند. ماندهٔ انواع مرخصیِ ردیابی‌شده بالای فرم همیشه دیده می‌شود؛ ثبت درخواست بیش از مانده ممکن است ولی پس از تأیید، مانده منفی می‌شود (هشدار به مدیر در رسیدگی).

**پیام‌ها:** تب «پیام» گفتگوی دوطرفه با مخاطبان مجاز (برای کارمند: مدیر شعبهٔ خودش + منابع انسانی/ادمین). از کادر «گفتگوی جدید» مخاطب را انتخاب کنید، پیام بفرستید؛ اگر گیرنده آنلاین باشد پیام هم‌زمان با WebSocket می‌رسد و بج نخوانده در نوار پایین به‌روز می‌شود. باز کردن گفتگو یعنی خواندن — پیام‌های طرف مقابل «خوانده شد» می‌شوند.

**اعلان‌ها:** تب «اعلان» تاریخچهٔ رویدادهای سیستمی است (تصمیم درخواست، رسیدگی تردد، تأیید اضافه‌کاری و …). با دکمهٔ «علامت‌گذاری همه» نخوانده‌ها پاک می‌شوند. توست زندهٔ بالای صفحه هم رویدادهای تازه را لحظه‌ای نشان می‌دهد.

**نصب PWA روی گوشی:** آدرس سرور را در مرورگر موبایل باز کنید و «Add to Home screen» بزنید؛ اپ به شکل برنامهٔ مستقل با آیکون اجرا می‌شود و آفلاین‌بودن جزئی (کش منوها) دارد.

## ۹. راهنمای کار — مدیر شعبه / منطقه

**رسیدگی:** تب «رسیدگی» (فقط برای نقش‌های مدیریتی) سه زبانه دارد:

- **درخواست‌ها:** پاره‌های در انتظارِ شعبه‌های شما. نام پرسنل، بازهٔ شمسی، ماندهٔ مرخصی او و هشدار «کسری مانده» دیده می‌شود؛ تصمیم (تأیید/رد) با توضیح اختیاری. اگر درخواست چندشعبه‌ای باشد، تأیید شما فقط پارهٔ شعبهٔ خودتان را قطعی می‌کند و وضعیت کل تا تصمیم سایر شعب «در انتظار» می‌ماند.
- **تردد نیازمند رسیدگی:** رویدادهای NEEDS_REVIEW (خارج از محدوده، دقت پایین، بدون مختصات، افست ساعت). برای تأیید، «زمان مؤثر» اصلاح‌شده با تاریخ شمسی + ساعت را بدهید (پیش‌فرض همان زمان دستگاه)؛ برای رد، ذکر دلیل الزامی است و رویداد با برچسب «رد فنی» حفظ می‌شود (حذف نمی‌شود). تصمیم به کارمند اعلان زنده می‌رسد.
- **اضافه‌کاری:** پیشنهادهای محاسبه‌شدهٔ سیستم؛ تأیید با کل مبلغ پیشنهادی.

**تابلوی شعبه:** زبانهٔ چهارم، وضعیت همهٔ پرسنل شعبه در یک تاریخ مشخص (شمسی) را یک‌جا نشان می‌دهد: ورود/خروج، کارکرد، تأخیر، غیبت، تردد ناقص و مرخصی‌ها.

**پیام و اعلان:** مدیر می‌تواند با پرسنل شعبهٔ خود و HR/ادمین گفتگو کند (تب پیام). تصمیم‌هایی که سایرین روی کارهای مرتبط با شما می‌گیرند به‌صورت زنده توست می‌شوند؛ صف رسیدگی پس از رویدادهای مرتبط خودکار تازه می‌شود.

**در اپ اندروید:** دکمهٔ «رسیدگی مدیر» فقط برای نقش‌های مدیریتی نمایش داده می‌شود و همان سه زبانه را با چیدمان موبایل ارائه می‌کند؛ تصمیم‌ها از اپ هم کاملاً معادل وب است.

## ۱۰. راهنمای کار — HR / ادمین

**ورود گروهی پرسنل:** تب «ورود گروهی» — ابتدا «قالب Excel» را دانلود کنید، پرسنل را (کد پرسنلی با حفظ صفرهای ابتدایی، نام، شعبه با کد، …) پر کنید و بارگذاری کنید. حالت پیش‌نمایش (dry-run) بدون تغییر داده، خطای هر سطر را گزارش می‌دهد؛ بعد تأیید نهایی. همین جریان برای «ماندهٔ مرخصی» اولیه (قالب seed LeaveLedger) هم هست.

**سازمان:** تب «سازمان» — تعریف منطقه‌ها، شعب و شیفت‌ها. برای هر شعبه می‌توانید ژئوفنس (عرض/طول جغرافیایی + شعاع مجاز) تعیین کنید؛ پانش‌های بیرون از شعاع به رسیدگی می‌روند نه رد. تخصیص شعبهٔ دوم به پرسنل (allow-list) هم همین‌جاست و مبنای شکست بازهٔ چندشعبه‌ای است.

**گزارش‌ها:** تب «گزارش‌ها» — گزارش ماهانهٔ HR (خروجی Excel سه‌برگه‌ای: خلاصهٔ ماهانه / ماندهٔ مرخصی / راهنما)، گزارش انتظامی تأخیر/غیبت (سطح کل شبکه یا یک شعبه)، گزارش سالانه + نمودار روند ۱۲ ماه جلالی. همهٔ خروجی‌ها RTL فارسی با تاریخ شمسی‌اند.

**پنل ادمین:** `http://دامنه/admin/` برای کارهای نادر مدیریتی (باز کردن قفل حساب، ویرایش مستقیم، دیدن اعلان‌ها). تغییرات ساختاری سازمان را ترجیحاً از تب سازمان بدهید نه ادمین، تا اعتبارسنجی‌های کسب‌وکار اجرا شوند.

## ۱۱. عیب‌یابی و نگهداری

| نشانه | علت محتمل | راه‌حل |
|---|---|---|
| `localhost` باز نمی‌شود / 502 | api بالا نیست یا هنوز Healthy نشده | `docker compose ps` و `docker compose logs api --tail 100` |
| صفحهٔ قدیمی بعد از به‌روزرسانی | Service Worker کش | یک بار Ctrl+Shift+R؛ در PWA نصب‌شده، بستن کامل اپ |
| 401 مکرر و خروج خودکار | انقضای refresh (۳۰ روز) یا تغییر رمز در دستگاه دیگر | خروج و ورود مجدد |
| «حساب موقتاً قفل است» | ۵ ورود ناموفق | چند دقیقه صبر یا باز کردن از پنل ادمین |
| «شعبه فعال با این کد یافت نشد» | کد شعبه در Excel اشتباه/غیرفعال | اصلاح کد در فایل یا فعال‌سازی شعبه در سازمان |
| پانش با برچسب UNAVAILABLE | مجوز GPS رد شده یا دقت پایین | طبیعی است — در صف رسیدگی مدیر تصمیم می‌گیرد |
| `git pull` ناموفق | تغییر محلی روی فایل‌های ردیابی‌شده | `git stash` سپس pull |
| «Docker یافت نشد» | Docker Desktop بسته است | اجرای Docker Desktop و تکرار update.ps1 |
| پیام‌ها/اعلان زنده نمی‌آید | سوکت بسته (پروکسی/شبکه) | رفرش صفحه؛ سوکت خودش reconnect می‌شود |

دستورات نگهداری روزمره: وضعیت سرویس‌ها `docker compose ps`، مصرف منابع `docker stats`، لاگ زندهٔ هر سرویس `docker compose logs -f api` (یا worker/scheduler/gateway/db). سلامت کلی با `/api/v1/health/` قابل مانیتورینگ است و می‌توانید در Zabbix/UptimeRobot همین URL را چک کنید. پیش از هر اقدام پاک‌سازی دستی روی دیتابیس، یک پشتیبان تازه بگیرید (بخش ۶) و برای تغییرات سیاست نگهداشت از کلیدهای `.env` استفاده کنید، نه حذف دستی رکورد.
